# Identity-provider and token-audience boundaries

This is the repository-owned contract linked by the
[trusted-provider skill](../../.codex/skills/configure-trusted-identity-providers/SKILL.md).

## Authentication configuration

- The data project and token-verification trust are separate configuration.
- A trusted provider is an exact issuer/audience pair. Discovery supplies its
  signing keys; signature, issuer, audience and temporal claims are mandatory.
- A browser origin, redirect URL or successful login is not a token audience.
- Exact operational identifiers belong in governed deployment configuration,
  not public prose, reusable examples or browser input.

## Authorization separation

A valid token authenticates a requester account only. It does not grant a
tenant, employee role, controller relationship, licence, selected subject,
clinical scope or emergency capability.

Keep OIDC/SMART requester `sub`, registered DCR client, selected human or
animal subject, tenant and clinical author/attester as distinct identities.
Subject access still requires the applicable relationship, scope and Consent.

Every deployment profile owns its explicit provider allowlist. Do not copy
trust between human and animal profiles, between products, or from staging to
production. Verify the effective pod configuration and a real authenticated
request before reporting a provider as supported.
