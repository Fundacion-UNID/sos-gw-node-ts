# Federated EHR and continuity-storage boundary

Status: extension scope. This document does not claim that federated EHR
login, multi-recipient continuity envelopes, DICOM recovery or a complete
emergency journey is implemented or deployed.

## Independent authorities

Keep these decisions separate:

1. the source EHR authenticates its professional and authorizes its own FHIR
   API through SMART;
2. the gateway validates exact `(iss, sub)` and verified `fhirUser` evidence;
3. the selected provider/index authorizes the subject, purpose, sections,
   operations and expiry, including any separate emergency decision; and
4. the continuity service applies its own retention, encryption, restore and
   deletion policy.

SMART launch context does not create a hosted tenant, controller, professional
licence or subject grant. Browser-supplied organization and email are not
authority. Preserve source authorship and provenance on projections,
communications and explicitly authorized write-back.

## Storage boundary

Metadata, encrypted objects, structured FHIR projections, imaging, audit and
jobs remain replaceable adapters with independent authorization. Infrastructure
encryption at rest is not an application-level member/device envelope.
Claims-first protected storage remains canonical inside this gateway; native
FHIR exists only at explicit import, projection or export boundaries.

Any implementation must add focused contracts and real boundary evidence under
the [local-first release contract](../LOCAL_FIRST_RELEASE_CONTRACT.md). Until
then, documentation and UI must label the capability as target scope.
